Despliegue MailySoft

Dos diagramas: la topología en Railway (nombres de servicio definitivos, líneas redibujadas para distinguirse al cruzar) y su equivalente en Azure con redes virtuales y NSG, que sí imponen de verdad quién habla con quién.

1. Railway

Backoffice y frontend con dominio público; las seis APIs y maily-db sin él. Las llamadas entre apps y APIs van en lila claro, las llamadas entre APIs en lila oscuro, el acceso a la base en azul — y uso curvas en vez de ángulos rectos para que, donde dos líneas se crucen, se note cuál es cuál.

acción de una persona Auth0 app pública → API API → API acceso a maily-db sin implementar / sin aprovisionar

Notas — Railway

  • Nombres de servicio: ya con la nomenclatura definitiva — maily-users-api, maily-system-api, maily-public-api, maily-clinics-api, maily-schedule-api, maily-patients-api.
  • Líneas: dos tonos de lila separan "app pública llamando a una API" de "API llamando a otra API", y todas usan curvas en vez de ángulos rectos. Reordené la fila de APIs para que maily-users-api (a quien le hablan tres de las otras cinco) quede al centro, con sus vecinas directas a cada lado; solo maily-clinics-api necesita saltar por encima de maily-system-api para llegar a ella, y esa es la única línea que lo hace. Con seis APIs hablándose entre sí, con la app pública y con una sola base, algún cruce entre líneas del mismo color es inevitable — por eso cada relación tiene su propio tono y las curvas lo marcan con un trazo limpio, no con un ángulo recto.
  • maily-schedule-api ya exige token (como confirmaste): su llamada a maily-users-api para confirmar el permiso ya se dibuja sólida, igual que la de maily-clinics-api.
  • Lo demás (exposición a internet, el límite real de la red privada de Railway, el gap de credenciales de maily-system-api, y que mover maily-db de Azure a Railway es trabajo real) sigue igual que en la versión anterior — ver el recuadro de advertencia en el propio diagrama.

2. Azure — la alternativa con aislamiento de red real

Mismo set de servicios, pero con lo que tú ya conoces: una VNet con tres subredes y un NSG por subred que de verdad decide quién puede hablarle a quién — a diferencia de Railway, esto sí se impone en la red, no solo en las credenciales. Las llamadas entre apps y APIs son las mismas que en el diagrama de Railway (no las repito todas); aquí lo nuevo es el límite de red.

acción de una persona Auth0 / login integración saliente hacia la VNet acceso a datos / secretos límite de subred impuesto por NSG

Notas — Azure

  • Esto es justo lo que pediste al abrir el tema: redes virtuales y NSG controlando de verdad quién llega a quién. En Azure sí hay un equivalente real a lo que describiste, a diferencia de Railway.
  • App Service vs. Container Apps para las seis APIs: ambos funcionan. Container Apps con un Environment interno no tiene FQDN público por defecto — el aislamiento es automático. Con App Service hay que deshabilitar el acceso público y añadir un Private Endpoint en subred-apis (o usar Access Restrictions "solo VNet"); el NSG de la subred por sí solo no bloquea el endpoint público de un App Service, porque ese endpoint no pasa por la subred.
  • Application Security Groups (ASG): son más para agrupar VMs o NICs y así escribir reglas de NSG sin depender de rangos de IP. Con App Service/Container Apps (sin VMs propias) no aplican directamente — aquí el control real es el NSG por subred más Private Endpoint/Access Restrictions. Si en el futuro corres algo en VMs o AKS, ahí sí valdría usar ASGs para no tener que mantener listas de IPs en las reglas.
  • maily-db: este diagrama representa cómo está desplegada hoy en la práctica (Azure Database for PostgreSQL Flexible Server) — es el que corresponde a tu infraestructura real actual, a diferencia del diagrama de Railway, donde la moviste ahí como destino nuevo.
  • mailySoft-DB (Flyway) necesita una excepción real: si subred-data solo acepta tráfico de subred-apis, el pipeline de migraciones (que corre fuera de la VNet, p. ej. en GitHub Actions) no puede llegar a maily-db sin ayuda. Las dos salidas usuales: un runner autoalojado dentro de la VNet, o una regla temporal del NSG-data que se abre solo durante el despliegue. Vale la pena decidir esto antes de cerrar subred-data del todo.
  • Azure Key Vault ya aparece en tu Terraform (azure_key_vault_id) — lo mantuve en el diagrama porque es donde deberían vivir DATABASE_URL y los secretos de Auth0, leídos por cada API vía Managed Identity en vez de variables de entorno planas.
